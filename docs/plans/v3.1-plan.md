# NyPi V3.1 Executive Precision, Evidence Dossiers & Live Board Streaming Plan

This specification is the post-`D86` (`b93f5438d`) code-review and precision-hardening pass. It closes three concrete
bugs found in the `D84`–`D86` implementation and lands the agreed executive quality upgrades across `Worker` reporting,
`Principal` 4-layer context hydration, anti-drop disposition gating, settlement coalescing, and live token/step
streaming on `nypi board`.

Execute **Part 1 (`D87`)** and **Part 2 (`D88`)** in order as two clean, tested commits (include `docs/v3.1-plan.md` in
the `D87` commit). Every commit must pass `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
`cargo test --workspace`, and `./scripts/build-board.sh && cargo build`.

## Part 1 (Decision D87): Bug Fixes, Worker Evidence Dossiers (`report.md`), Disposition Gate & Settlement Coalescing

### 1.1 Fix Three Concrete Bugs Found in `D84`–`D86` Code Review

1. **Restore `workspace` and `goal` (`campaign`) when resuming interrupted tasks**
   - **Where**: `crates/nypi-core/src/runtime/tasks.rs` (`Runtime::resume_task`).
   - **Defect**: `Ledger` records `record.workspace` and `record.goal_id` / `record.spawned_by_activation`, but
     `resume_task` does not restore them onto `Runtime` before continuing the session, causing crash-recovered tasks to
     lose both `<project_plan>` and `<task_workspace>`.
   - **Fix**: Restore `workspace` and `(goal_id, spawned_by_activation)` from `TaskRecord` inside `resume_task` before
     rebuilding prompt sections and continuing the run. Add a regression test verifying a resumed campaign task still
     pins `<project_plan>` and `<task_workspace>`.

2. **Hot-reload `SecretScrubber` when `secrets.enc` changes in a long-running daemon/board**
   - **Where**: `crates/nypi-core/src/chat.rs` (`scrubber_for`), `crates/nypi-core/src/principal.rs`,
     `crates/nypi-vault/src/secrets.rs`.
   - **Defect**: `Chat` and `Principal` construct `SecretScrubber` once at startup (and return an empty scrubber forever
     if `secrets.enc` did not exist when the daemon first booted). Secrets added later via `nypi secrets set` are not
     scrubbed from `chat/turns.jsonl`, `principal/activations/*.jsonl`, or `stores/decisions.jsonl` until restart.
   - **Fix**: Introduce a lightweight `LiveScrubber` in `nypi_vault::secrets` that caches `(mtime, len)` of
     `secrets.enc` and reloads `SecretScrubber` only when the file appears or changes (never prompting Keychain if the
     file does not exist). Share `LiveScrubber` across `Chat` and `Principal`. Add a unit test adding a secret after
     module startup and verifying subsequent logs scrub it.

3. **Restore `<portrait>` and Cache-Stable Prefix in `Principal`**
   - **Where**: `crates/nypi-core/src/principal.rs` (`system_prompt`, `809–848`).
   - **Defect**: `Principal::system_prompt` omitted `<portrait>`, and embedded `## Tasks` (containing per-second elapsed
     counters `"Running for 14 s..."`) plus per-activation `## Where` directly inside `system_prompt`, invalidating
     provider prefix caching on every turn.
   - **Fix**: Keep `Principal`'s `system_prompt` cache-stable (`principal.md` + `<portrait>` + `<self>`), moving dynamic
     per-activation situational sections into the 4-layer activation opening envelope (Section 2.1 below).

### 1.2 Structured Worker Dossier Trilogy (`brief.md` + `findings.md` + `report.md`) & `inspect_task_evidence`

- **Where**: `crates/nypi-core/src/task_pool.rs`, `crates/nypi-core/src/runtime/run.rs`,
  `crates/nypi-core/prompts/core.md`, `crates/nypi-core/src/principal.rs`.
- **Change**:
  1. **Workspace `report.md` Requirement**:
     - For any task running with a Vault workspace (`10-workspaces/YYMMDD-<slug>/`), instruct the Worker (`core.md` and
       `<task_workspace>`) to write `report.md` in its workspace via `vault_write` before ending `Done` or `Blocked`:
       - `## Contract Check` (item-by-item check against `brief.md`'s `Done when`);
       - `## Key Findings & Deliverables` (exact file paths, numbers, and inline references to both `[tN]` tool calls
         and `findings.md`);
       - `## Falsified Paths & Residual Risks` (dead ends ruled out with `[tM]`, remaining caveats, or concrete options
         when `Blocked` at an authority boundary).
     - When a workspace-backed Worker run proposes `Done` on a real model (`model.api != Api::Faux`, or when opted in by
       test setting) without having written `report.md` (or with zero verified `[tN]` references after running tools),
       nudge once inside the Worker loop to write `report.md` with verified `[tN]` citations before settling.
  2. **Harness-Generated `Evidence Manifest` (Unforgeable Appendix)**:
     - When building `Trigger::TaskSettled` (`review_note`), read `report.md` (falling back to `answer`), and have the
       harness append a machine-extracted **`## Harness Evidence Manifest`** listing:
       - Every `[tN]` cited in `report.md`/`answer` resolved against the task's `SessionStore`: tool name, compact
         arguments, exit/error status, duration, and a verbatim output excerpt (`<= 400` chars each);
       - Any mutating tool calls (`write`, `edit`, `bash`) and whether at least one read/verification tool ran *after*
         the final file mutation (flagging an explicit warning if the task mutated files and ended `Done` with no
         subsequent check!).
  3. **`inspect_task_evidence` Tool on `Principal`**:
     - Add `inspect_task_evidence({ task_id, refs: ["t3", "t8"] })` to `Principal`'s tools, reading the task's local
       `SessionStore` file (`TaskRecord.session_path`) in-process in milliseconds (scrubbed via `LiveScrubber`, capped
       at `8,000` chars per call) so `Principal` can inspect full raw stdout/diffs of any step whenever a claim looks
       suspicious.

### 1.3 Explicit `Disposition` Gate (Zero Silent Drops) & `batch_unless_failed` Settlement Coalescing

- **Where**: `crates/nypi-core/src/principal.rs`, `crates/nypi-core/src/task_pool.rs`,
  `crates/nypi-core/prompts/principal.md`.
- **Explicit Disposition Contract**:
  - Add a lightweight tool `conclude_activation({ disposition: "already_handled" | "waiting_on_running_task" | "noted_only", reason })`
    to `Principal`.
  - Track on `Activation.work` whether the activation performed at least one concrete disposition: started/steered/continued/cancelled
    a task, modified `goals`/`schedule`, called `stimulate_chat`, or explicitly called `conclude_activation` (for `P2`
    idle activations, replying `NOTHING` also counts).
  - If a `P0` (`UserSignal`) or `P1` (`TaskSettled` / `SchedulePrompt`) activation ends its turn (`StopReason::Stop`)
    with **zero** dispositions (on non-`Faux` models, or when `principal.enforce_disposition` is enabled in tests),
    inject **one** automatic nudge into that activation:
    *"You ended this activation without dispatching/updating any task, sending `stimulate_chat`, or calling
    `conclude_activation` with a reason. Complete the required action so the owner's request never drops silently."*
- **Same-Goal Settlement Coalescing & `batch_unless_failed`**:
  - Add optional `review_policy: "immediate" | "batch_unless_failed"` (default `"immediate"`) to `Principal`'s
    `start_task`.
  - When a `batch_unless_failed` task settles as `Done` while sibling tasks of the same `goal` (or same
    `spawned_by_activation`) are still actively running in `TaskPool`, hold its review briefly (up to `60s` or until
    siblings settle; **never** hold `Blocked` or `Failed`, which wake `Principal` immediately!).
  - Furthermore, whenever `Principal::next()` pops a `Trigger::TaskSettled`, coalesce any other `TaskSettled` items
    currently waiting in `queued` for the same `goal` (or batch) into a single combined `TaskSettledBatch` review
    activation so `Principal` audits sibling deliverables together in one pass.

## Part 2 (Decision D88): 4-Layer `Activation` Context Hydration & Live Streaming on Glass-Box `Board`

### 2.1 Four-Layer `Activation` Context Architecture (`principal.rs`)

Structure every `Principal` activation's context cleanly into four concentric rings:

1. **Ring 1 — Cache-Stable System Prompt**:
   - `principal.md` charter + `<portrait>` + `<self>` (identical across turns and activations -> maximum KV-cache hit
     rate).
2. **Ring 2 — Global Situational Radar (`<situational_radar>` at head of activation opening message)**:
   - Compact live `Goals` radar enriched by `campaign::clocks` (`due in Nd`, `idle Nd`, active task count, project
     path);
   - Compact `Execution Board`: active/waiting `TaskPool` tasks, `Principal`'s own `Suspended` & `Queued` summaries,
     upcoming schedules within 48h, `## Where` focus, and `<devices>`;
   - `<recent_decisions>` (newest `15` entries from `DecisionJournal`).
3. **Ring 3 — Trigger-Specific 5ms Pre-Hydrated `<briefing_pack>`**:
   - Before the first model call of an `Activation`, run a fast (<5ms, non-blocking, BM25 + cached vectors when already
     loaded; never block waiting for a cold model download) local lookup using the trigger's topic/text:
     - **`P0 UserSignal`**: If a `Goal` or `10-projects/<slug>/plan.md` matches -> **inline `plan.md` in full** (up to
       6 KB); for top-matching `30-entities/` & `20-playbooks/` notes in `VaultIndex` -> include **only matched chunk
       excerpts + 1-hop `[[WikiLink]]` neighbor list** (preventing context noise; `Principal` calls `vault_read` when
       deeper detail is needed); plus top `MemoryValve` episodic facts and matching `AssetRegistry` handles (`cred://...`).
     - **`P1 TaskSettled` (or `TaskSettledBatch`)**: `brief.md` + `report.md` + `findings.md` + `Harness Evidence
       Manifest` + **full parent `10-projects/<slug>/plan.md`** (when `goal` is set) + newest 3 `PrimaryStream` messages.
     - **`P1 Inbound` / `SchedulePrompt`**: Fenced raw inbox note or schedule output + matched `plan.md` & `30-entities/`
       excerpts from `VaultIndex`.
     - **`P2 Idle`**: Two-clock `goal_digest` (`Deadlines` × `Neglect`) + untriaged `00-inbox/` list + remaining DMN
       budget.
4. **Ring 4 — Local Activation Transcript & `<resumption_delta>`**:
   - Multi-step reasoning & tool calls scoped strictly to this activation, plus `<resumption_delta>` when resumed after
     preemption.

### 2.2 Live Streaming & Dossier Rendering on Web `Board` (`nypi-board-*`, `cli/src/board/`)

Close the remaining `D86` observability gap (`roadmap.md:181`: *"chat's and the Principal's text is shown per turn, not
streamed as it is written"*):

1. **Live Plane Step & Delta Streaming**:
   - Publish lightweight plane progress events over `BoardLink` (or SSE watcher) as `Chat` and `Principal` run: current
     step (`Thinking`, `Reading <tool>`, `Calling <tool>`, `Writing` delta tail), so `/` (`Now` Three-Plane Cards),
     `/chat`, and `/activation/:id` show live token/tool activity **while a turn or activation is in flight**, not only
     after it finishes!
2. **Render `report.md` & `Harness Evidence Manifest` on `/task/:id` and `/activation/:id`**:
   - On `/task/:id`, show the Workspace Trilogy (`brief.md`, `findings.md`, `report.md`) as clean tabbed/collapsible
     Markdown panels alongside the verified `[tN]` badges.
   - On `/activation/:id`, show the expandable `<briefing_pack>` (what Vault notes/plans/assets were pre-hydrated for
     that activation) and any `Disposition` badge (`stimulated_chat`, `tasks_touched`, or `conclude_activation` reason).
3. **Rebuild Embedded WASM Assets**:
   - Run `./scripts/build-board.sh` and `cargo build` so `crates/nypi-cli/assets/board/` embeds the updated WASM & CSS,
     and extend `crates/nypi-cli/src/board/tests.rs` to test the new fields and live plane events.
