# NyPi V3.3 Tech-Debt Cleanup & Documentation Consolidation Plan

This specification sweeps clean the remaining historical code seams, module bloat, and documentation debt left after
`D90` (`9896e6cfe`), before live model benchmarking and daily rollout begin.

Execute **Part 1 (`D91` — Code & Module Cleanup)** and **Part 2 (`D92` — Documentation Reorganization & Current-State
Rewrite)** in order as two clean, tested commits. Every commit must pass `cargo fmt --check`,
`cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` (zero network calls in tests), and
`./scripts/build-board.sh && cargo build`.

## Part 1 (Decision D91): Sweep Remaining Code & Structural Tech Debt

### 1.1 Remove Retired `D38` Remnants from `Thinking` (`crates/nypi-core/src/thinking.rs`, `runtime/mod.rs`)

Since `D84`, `Thinking` has one job only: observing a running worker task (`spawn_observer`). Clean up two leftovers from
the retired conversational second-look design:
1. Remove the redundant `observe_worker: bool` field from `ThinkingSettings` so `enabled: bool` is the single switch
   controlling the observer (`#[serde(default)]` already tolerates legacy `"observeWorker"` keys in existing
   `settings.json` files without failing deserialization). Update `Runtime` (`crates/nypi-core/src/runtime/mod.rs`) and
   any tests/docs referencing `observeWorker`.
2. Remove the unused `asked: String` and `watch: Vec<String>` fields from `Thought` (keeping `approach` and `say`, which
   `spawn_observer`, the pulse bus, and the board read).

### 1.2 Apply Safe Allowlisted `PlaceContext.trusted_settings` on Remote Focus (`crates/nypi-core/src/runtime/mod.rs`)

Currently, a remote `Node` reads `.nypi/settings.json` in a trusted folder (`device.rs:124`) and sends it in
`PlaceContext.trusted_settings`, which `Runtime::apply_place_context` (`runtime/mod.rs:1196`) silently discards.

Close that gap **without letting a remote `Node` weaken `Hub` security (`D80`)**:
- In `Runtime`, retain the Hub's base values for the allowlisted per-run settings and restore them whenever
  `apply_place_context` runs before applying the current remote folder's `trusted_settings` (matching how `remote_added`
  restores `skills` and native `specialists`).
- Apply **only** this safe allowlist from `PlaceContext.trusted_settings`:
  - `defaultThinking` (updating the runtime's thinking level, clamped to the current model's supported levels);
  - `compaction` (`enabled`, `reserveTokens`, `keepRecentTokens`);
  - `retry` (`enabled`, `maxRetries`, `baseDelayMs`, `maxAgentDelayMs`);
  - **Additive-only** `approval.tools` (a trusted remote folder may add tool names that require user approval on the Hub,
    never remove Hub-configured ones and never set `approval.mode` to `"off"`).
- Explicitly ignore Hub-owned or security-sensitive keys (`approval.mode`, `envFiles`, `mcpServers`, `sandbox`,
  `channels`, `hub`, `board`, `commandTools`).
- Add a test verifying that when focused on a remote trusted folder, additive `approval.tools` and `retry` /
  `defaultThinking` from `PlaceContext.trusted_settings` take effect and revert when focus moves elsewhere, while
  `"approval": { "mode": "off" }` and `"envFiles"` from the remote node are ignored.

### 1.3 Move Telegram Under `channels/` & Support `SecretStore` Bot Tokens (`crates/nypi-hub/src/channels/telegram/`)

Bring Telegram into the `D81` channel layout and `D77` secret-store rules:
1. Move `crates/nypi-hub/src/telegram.rs` and `crates/nypi-hub/src/telegram_channel.rs` under
   `crates/nypi-hub/src/channels/telegram/` (for example `channels/telegram/api.rs` and `channels/telegram/mod.rs`,
   updating `crates/nypi-hub/src/lib.rs`, `notify.rs`, `nypi-cli`, and `crates/nypi-cli/src/board/topology.rs`'s module
   `source` path; keep thin re-exports only if helpful for cleanliness).
2. Add `TelegramChannelSettings` under `ChannelsSettings` in `crates/nypi-core/src/config.rs`:
   - `bot_token_secret: Option<String>` (`settings.channels.telegram.botTokenSecret`, accepting a `cred://...` handle,
     defaulting to `None`).
   - When resolving the Telegram bot token (for both the daemon channel and `Notifier`), read `botTokenSecret` from
     `SecretStore` (`nypi_vault::secrets::SecretStore`) first when set—so the token is sealed at rest and scrubbed
     everywhere by `LiveScrubber`—and fall back to `TELEGRAM_BOT_TOKEN` via `lookup_env` so existing setups continue
     working unchanged. If `botTokenSecret` is configured with an invalid handle or missing secret, log a clear message
     and keep the channel off (matching `channels/webhook.rs`).
   - Add a unit test verifying `TelegramChannel` / token resolution reads `cred://channels/telegram` from `SecretStore`
     without `TELEGRAM_BOT_TOKEN` in the environment.
